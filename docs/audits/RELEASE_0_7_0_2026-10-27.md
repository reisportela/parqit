# parqit 0.7.0 candidate validation

Date: 27 October 2026. Scope: prepare the next minor release, finish the
analytical and data-option expansion of `collapse`, update both helps, and
check whether the ordinary aggregation path has acquired measurable cost.
All builds and executions in this preparation use **DuckDB 2.0.0**. No work
on DuckDB 1.5.6 is included.

## Release surface

The [aggregation comparison](GCOLLAPSE_PARITY_2026-10-27.md) records the
implemented statistics, weight families, sample controls, merge-back,
patterns, labels and storage options. It also records deliberate differences
from gcollapse: lazy execution, existing precision and missing-value rules,
and exclusion of gtools-specific engine switches. `pivot` shares the added
unweighted statistics; its separate syntax does not accept collapse's
weight/data controls.

The package, CMake project, ado/plugin compatibility check, citation and all
ten dialog banners identify 0.7.0. The numerical contract remains 4. The
Collapse options tab stays within the compact native dialog layout. Native
Stata dialogs retain their fixed window dimensions.

Both helps now document weights consistently, including their summaries.
The row-context and materialisation limits were checked against the current
implementation: transformation expressions support their documented `_n` and
`_N` contexts; read-only `count if` and `list if` retain their restrictions;
the plugin's transfer-index limit applies to eager loading/collection rather
than all lazy views or Parquet saves.

The integration runner accepts an optional `STATA_PYTHON_EXEC` pointing to an
existing oracle environment. It selects Python inside each runner-owned
batch process, without changing permanent Stata settings or installing
packages. This removes a local environment blocker from the footer-precision
oracle; it does not alter package execution.

## Performance check

A focused comparison was warranted because all collapse requests pass
through the extended dispatcher and the feature adds numerical kernels.
The ordinary unweighted path still delegates to the original compiler.

`performance.py` compares a reconstructed pre-expansion binary with the
0.7.0 candidate, using the same compiler, pinned DuckDB 2.0.0 archive, four
threads and a 1 GB engine memory limit. The before binary is diagnostic;
its recorded reconstruction and ABI checks are in the aggregation audit.
Two public synthetic datasets contain 600,000 and 6,000,000 rows, with 5,000
groups. Each version has three interleaved process runs, one warm-up and two
measurements per scenario per process, giving six measured observations per
version/scenario. The script separates view opening, plan construction and
collection, records host load and process resources, and compares emitted
SQL and materialised numeric payloads.

All eight scenarios passed exact SQL and payload identity. Median seconds:

| Rows | Scenario | Plan before | Plan 0.7.0 | Execution before | Execution 0.7.0 |
|---|---|---:|---:|---:|---:|
| 600,000 | Grouped | 0.0030 | 0.0030 | 0.1130 | 0.1030 |
| 600,000 | Filtered | 0.0040 | 0.0030 | 0.0570 | 0.0475 |
| 600,000 | Derived source | 0.0030 | 0.0030 | 0.0970 | 0.0990 |
| 600,000 | Global | 0.0025 | 0.0030 | 0.0190 | 0.0315 |
| 6,000,000 | Grouped | 0.0045 | 0.0030 | 0.2765 | 0.2285 |
| 6,000,000 | Filtered | 0.0050 | 0.0050 | 0.1185 | 0.1440 |
| 6,000,000 | Derived source | 0.0030 | 0.0030 | 0.2120 | 0.2210 |
| 6,000,000 | Global | 0.0020 | 0.0030 | 0.0475 | 0.0530 |

Planning cost has no consistent increase in this sample. Execution medians
move in both directions and do include slower observations: for example,
the six-million-row filtered median rises from 0.1185 to 0.1440 seconds.
Its measured ranges overlap almost completely (0.094–0.213 versus
0.097–0.211 seconds). Global medians also rise, at much smaller absolute
times. The shared host load was about 29–34. Process maximum RSS ranges were
184,596–201,572 KiB before and 186,232–190,504 KiB after.

The evidence supports fidelity and comparable planning cost for these
workflows. It does **not** certify a universal speed-up or the absence of
every performance regression. No precision trade-off or performance
optimisation is introduced in response to these dispersed timings. A
larger campaign is justified if a concrete workload shows a repeatable loss;
repeating short noisy tests is not a substitute for that evidence. The
bounded Gini spill check in the aggregation audit covers a new numerical
path, but is not an old/new performance comparison.

Machine-readable timings, individual samples, resource/load observations and
the limitations are in `performance/receipt.json`.

## Publication boundary

This document records a local candidate. It is not evidence of a published
0.7.0 release. A published release requires the exact Linux, Windows, macOS
Intel and macOS ARM CI assets from the chosen commit, checksum and identity
checks, staged-install verification of those assets, and public readback.
The local candidate must not be relabelled as that CI-built distribution.

Local review artefacts in the evidence directory are
`parqit-0.7.0-source-candidate.zip` and
`parqit-0.7.0-linux-local-candidate.zip`. They include internal file manifests
and a candidate notice; `package_receipt.json` records the archive hashes.
The source archive excludes unrelated local modifications and includes the
eight explicitly added feature/test/audit files. `candidate_paths.txt` lists
the 35 proposed source/documentation paths and `candidate_changes.patch`
captures their changes relative to the base commit. No commit, push, tag,
publication or global installation was performed during this preparation.
