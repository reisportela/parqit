## (b) Findings

Severity scale as briefed: S2 gap/inaccuracy; S1 help promises something the code refuses, or the code silently
does something the help contradicts; S0 a documented claim hides a data-integrity loss.

### A5-1 — S1 — `encoding()` is silently accepted and ignored on the lazy (view) save path; the help says any other name is refused
- **Where:** help `{marker materialisers}`, paragraph `{opt encoding(name)} names the legacy 8-bit code page …`:
  "Any other name is refused before anything is written. It matters for a save of the dataset in memory; a lazy
  Parquet-to-Parquet save carries UTF-8 already."
- **Code:** `_parqit_save` parses `ENCoding(string)` for both paths but only the memory path sends `_sq_encoding`
  (`_parqit_wr_save_request`); `_parqit_wr_view_save_request` has no `encoding` field and `cmd_view_save` never
  validates it. Probe P1: with a view open, `parqit save out_enc.parquet, replace encoding(bogus)` → **rc 0, file
  written**; `encoding(latin9)` → rc 0, ignored. On the memory path `encoding(bogus)` → rc 198 (P2c) as documented.
- **Why it matters:** the dialog `parqit_write.dlg` emits `encoding(...)` for view saves as well; a user who
  changes it believes it took effect.
- **Suggested wording** (if the behaviour stays): "On a save of the dataset in memory any other name is refused
  before anything is written. On a lazy view save the option is accepted but has no effect: the view already holds
  UTF-8 (a `.dta`/Excel source was transcoded with the default code page when its bridge was written — see Input
  formats)." Preferred remedy is in code: validate `encoding()` on both paths (refuse unknown names) and either
  forward it or refuse it on the view path.

### A5-2 — S1 — Adapter bridges transcode legacy 8-bit text silently, with no `encoding()` and no note/r()
- **Where:** help `{marker formats}` Input formats ("… snapshots them to a small Parquet bridge the engine then
  scans; their variable/value labels and formats ride along"); `{marker materialisers}` String encoding ("Every
  save that transcodes anything prints a `note:` with counts and returns r(transcoded_…)"); `{marker options}`
  ("`parqit open _data` … reports any extended-missing collapse or fractional-date rounding caused by that
  snapshot"); README › Limitations › Legacy text. `encoding()` exists only on `parqit save`.
- **Code/evidence:** `_parqit_import_to_bridge` runs `quietly { … parqit save "bridge", replace data }` — the
  transcoding note and the `r(transcoded_*)`/`r(encoding)` results are dropped and the code page is always
  `windows-1252`; `_parqit_open` re-surfaces only `ext()`/`frac()` (not `transvars/transcells/transmeta/encoding`).
  Probes P7 (lazy `parqit use using legacy.dta`), P8 (eager), P9 (`parqit open _data` on legacy data), R6 (`parqit
  merge … using legacy_firms.dta`): labels `Regi\xe3o`/`N\xedvel`/`R\xf3tulo` arrive as `Região`/`Nível`/`Rótulo`
  with **no note and no r()**; R4: `parqit use using legacy.dta, encoding(latin9)` → rc 100 "filename required"
  (no such option; the message is also misleading).
- **Suggested wording** (Input formats, after "ride along"): "Because a bridge is a `parqit save` of the imported
  frame, the write-side conversions apply to it: legacy 8-bit text is transcoded from windows-1252 (there is no
  `encoding()` on `parqit use`/two-table adapters — convert a Latin-9/MacRoman `.dta` with `use` + `parqit save,
  encoding()` or `unicode translate` first), extended missings collapse to `.`, and fractional date/period counts
  are rounded; these conversions are currently not reported for a bridge." Preferred remedy in code: return
  `r(transcoded_*)`/`r(ext_missing)`/`r(frac_dates)` from `_parqit_import_to_bridge` and print them through
  `_parqit_lossy_notes` (as `_parqit_open` already does for two of them); add `encoding()` to `parqit use`/adapters.

### A5-3 — S0 (doc side S1) — `.dta` adapter bridges silently collapse `.a`–`.z` to `.` and round fractional dates; the help states parqit warns/names the column
- **Where:** help `{marker limitations}` bullet "Extended missings .a-.z become plain missing in Parquet …; parqit
  warns when they are written"; `{marker types}` Dates: "Saving a fractional day, millisecond or period count rounds
  … on both memory and lazy paths, and names the affected column"; `{marker formats}` gives no hint that a `.dta`
  read through the adapter changes values. README › Limitations › Extended missings ("`parqit save` warns when
  this loses information").
- **Evidence:** probe S1/S2 (`a5_probes4.log`): `extm_frac.dta` with `e = .a` and `d = td(01jan2020)+0.5`;
  `parqit use using extm_frac.dta` (lazy) and `…, clear` (eager) and `parqit merge m:1 id using extm_frac.dta`
  → no note at all; the loaded data shows `e = .` and `d = 02jan2020`. (`parqit open _data` does print both
  notes — Q9 — so only `_parqit_import_to_bridge`'s `quietly` is silent.)
- **Why S0 by the brief's definition:** a documented claim ("parqit warns when they are written"; labels/formats
  "ride along") hides a real, silent value change on a read path a user regards as lossless. If the panel prefers
  to treat it as a code defect, the documentation-side severity is S1.
- **Suggested wording:** see A5-2; plus in Limitations: "… parqit warns when they are written by `parqit save`
  or `parqit open _data`; a `.dta` bridged by `parqit use`/`merge`/`append`/`joinby` applies the same collapse
  without a note (read the file with `use` and `parqit open _data` to see the note)." Remedy in code preferred.

### A5-4 — S2 — Read-side refusal of invalid UTF-8 in a foreign Parquet file is undocumented
- **Where:** help has only the write-side story (`{marker materialisers}` String encoding); `{marker types}`
  says nothing about a foreign file whose VARCHAR payload is not valid UTF-8. ASSUMPTIONS #94 states "The read side
  (ENC1, v52) is unchanged: a foreign file with invalid UTF-8 payload still refuses loudly" (engine decoder error,
  pinned by `tests/verify_suite/v52_read_hardening.do`).
- **Suggested wording** (Type mapping › Special and unsupported values, or String encoding): "On read, parqit never
  transcodes: a Parquet file whose string payload is not valid UTF-8 is refused by the engine with a loud error
  naming the column; rewrite the file as UTF-8 at the source."

### A5-5 — S2 — Transcoding that widens a `str#` past 2,045 bytes promotes it to `strL` (ASSUMPTIONS #94) — not in the help
- **Where:** `{marker materialisers}` String encoding: "A str# whose transcoded values are longer is recorded
  wider, exactly as unicode translate widens it."
- **Suggested wording:** append "… and, past 2,045 bytes, is recorded as `strL` (the `parqit.*` metadata is
  built after the data pass, so the recorded type always matches the written values)."

### A5-6 — S2 (minor) — `encoding()` aliases and `r(encoding)` canonicalisation; `r(transcoded_vars)` absence
- **Where:** `{opt encoding(name)}` paragraph lists aliases `cp1252`, `iso-8859-1`, `iso-8859-15`; `{marker results}`
  Writing says "locals r(transcoded_vars) and r(encoding) … the variable list empty when nothing needed transcoding".
- **Code:** `legacy_encoding_parse` also accepts `windows1252`, `latin-1`, `iso8859-1`, `latin-9`, `iso8859-15`,
